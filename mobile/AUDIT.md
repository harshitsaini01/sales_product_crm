## CRITICAL

### [bug] Activity recreation (rotation/process death) re-dials and loses dialer state
- **File:** `app/src/main/java/com/tutelage/crm/counsellor/autodialer/CampaignRunnerActivity.kt`  
- **Where:** onCreate() ~L119-147, ensurePermissionsThenStart()/beginLoop() ~L149-170  
- **Problem:** All call-cycle state lives in Activity instance fields (seenOffHook, hangupQueued, playbackFired, lastDialedDeviceCallId, lastCallStartMs, currentRecordingId, currentCampaignContactId, mediaPlayer), NOT in the ViewModel or SavedStateHandle. On any Activity recreation — screen rotation, configuration change, or process death/restoration while a call is in progress — onCreate() unconditionally calls ensurePermissionsThenStart() which calls beginLoop() -> vm.start() -> vm.fetchNext() -> dialAndLog() -> placeCall(). Concrete scenario: counsellor is mid-call on contact N (OFFHOOK seen, recording about to play). Phone rotates or the OS recreates the Activity. The recreated Activity has seenOffHook=false and immediately fetches the NEXT contact from the server and fires a SECOND ACTION_CALL while the first call is still live — double-dial plus a skipped/abandoned contact whose status is never finalized. After process death the in-flight call's IDLE is also never observed by this Activity, so its RINGING DB row is left dangling (only later swept by staleRinging).
- **Fix:** Guard auto-start so it only runs on first creation: only call ensurePermissionsThenStart()/beginLoop() when savedInstanceState == null AND the VM is not already running/in-call. Move per-call transient state (seenOffHook, hangupQueued, playbackFired, lastDialedDeviceCallId, currentRecordingId, currentCampaignContactId) into the ViewModel (or SavedStateHandle) so a recreated Activity resumes the existing call cycle instead of starting a new dial.
- **Verifier note:** Two minor refinements, neither of which weakens the bug: (1) Calling ACTION_CALL while a GSM/VoLTE call is already active does not always literally place two simultaneously-ringing calls — depending on OEM/RIL the system typically holds the first call and dials the second, or in some cases ignores the request. But it does initiate a new outbound call to a different number and, more importantly, server-side the next contact has already been popped to 'dialing' and is then abandoned, so the user-facing harm (unintended extra dial + a silently skipped/never-finalized contact + a dangling RINGING row) holds regardless. (2) The proposed 'savedInstanceState == null' guard alone fixes rotation/config-change but NOT process death (where the OS may pass a non-null Bundle on restore yet the VM and all instance fields are gone); the deeper fix — moving call-cycle state into the ViewModel/SavedStateHandle and resuming rather than re-dialing — is the correct mitigation, as the claim's fix section also states.

### [security] Self-update APK installed with no signature/checksum verification (RCE)
- **File:** `app/src/main/java/com/tutelage/crm/counsellor/update/AppUpdater.kt`  
- **Where:** startDownload() ~L49-64 and installApk() ~L69-77; ApkInstallReceiver.onReceive() ~L22-47  
- **Problem:** The in-app updater downloads an APK via DownloadManager to external-files storage and then immediately fires the system installer on it (ACTION_VIEW with application/vnd.android.package-archive) without ANY integrity check. The release DTO carries a `sha256` field (AppReleaseDto.sha256) but a code search confirms it is never read anywhere outside the data class — no MessageDigest, no checksum compare, no APK signing-cert/signature verification before install. Combined with usesCleartextTraffic=true and an http:// base URL, a network MITM (or a compromised/typo'd CDN host) can swap the downloaded bytes for a malicious APK, which the app then prompts the user to install with REQUEST_INSTALL_PACKAGES granted. This is full remote code execution on the counsellor's device, which holds student PII, call recordings, and the auth token.
- **Fix:** Before calling installApk(), compute SHA-256 of the downloaded file and compare (constant-time) against release.sha256; abort and delete the file on mismatch. Additionally verify the downloaded APK's signing certificate matches the running app's signer via PackageManager.getPackageArchiveInfo(..., GET_SIGNING_CERTIFICATES) before launching the installer. Serve the APK and the release metadata strictly over HTTPS so the expected hash itself can't be tampered with.
- **Verifier note:** Two precision points that do not change the verdict but refine the runtime picture: (1) The download URL is built from API_BASE_URL + a fixed path, NOT from release.fileUrl — so the MITM vector is the cleartext app API channel itself, and tampering with the redirect/bytes (or also poisoning /latest to advertise a higher versionCode) drives the swap. (2) This is user-assisted, not zero-click, RCE: the OS package installer still presents an install-confirmation UI and the Android 8+ unknown-sources gate, so the counsellor must tap Install. The updater habituates exactly that tap, and combined with cleartext + no hash/signature check the practical risk remains critical. The proposed fix (constant-time SHA-256 compare against release.sha256, signing-cert match via getPackageArchiveInfo(GET_SIGNING_CERTIFICATES), and HTTPS-only for both metadata and APK so the expected hash can't itself be tampered) is correct and necessary.

### [security] APK update is installed with no signature or SHA-256 checksum verification
- **File:** `app/src/main/java/com/tutelage/crm/counsellor/update/AppUpdater.kt`  
- **Where:** startDownload() ~L49-64, installApk() ~L69-77; ApkInstallReceiver.onReceive ~L35-45  
- **Problem:** The release DTO carries `sha256` (AppReleaseDto.sha256) and `sizeBytes`, but neither is ever used. The APK is downloaded over DownloadManager and then handed straight to the system installer in installApk() with zero integrity verification. There is no SHA-256 digest comparison against AppReleaseDto.sha256, no size check, and no signing-certificate check. Combined with `usesCleartextTraffic="true"` in the manifest and a plain `${API_BASE_URL}/download` URL, a network MITM (or a compromised/wrong base URL) can substitute an arbitrary APK that the app will silently stage for install with REQUEST_INSTALL_PACKAGES. This is a full remote-code-execution vector on the counsellor's device.
- **Fix:** Before calling installApk(), compute the SHA-256 of the downloaded file (MessageDigest) and compare constant-time against release.sha256; also verify file length == sizeBytes. Reject and delete the file on mismatch. Strongly prefer HTTPS (remove usesCleartextTraffic, or restrict via network-security-config) and optionally verify the embedded APK signing certificate matches the current app's signer before install.
- **Verifier note:** Minor calibrations, not refutations: the final install is still gated by the OS's standard install-confirmation dialog (staging is silent, but the install tap is user-mediated), so 'silently stage for install' is accurate while a fully silent install is not. The claim also omits Android's same-signer enforcement on app updates, which would normally block an arbitrary differently-signed APK; however, because release builds use the shared debug keystore (build.gradle.kts L45), that mitigation is effectively defeated, so the practical risk is as bad as or worse than described. Exposure is conditional on cleartext/HTTP or a compromised base URL rather than unconditional, but the app itself ships cleartext-enabled with an HTTP default and no transport hardening, so it provides none of the defense-in-depth that the unused sha256 field was meant to supply.

## HIGH

### [security] Release build signed with the debug keystore
- **File:** `app/build.gradle.kts`  
- **Where:** android.buildTypes.release ~L41-46  
- **Problem:** The release build type sets signingConfig = signingConfigs.getByName("debug"). The debug keystore ships with the Android SDK and its credentials are public/identical across machines, so the release APK is signed with a key any developer or attacker possesses. This destroys the security guarantee of APK signing: an attacker can build a malicious update signed with the SAME debug key and Android will accept it as a legitimate same-signer update (and it would also pass any naive same-signer check added to the updater). Update integrity and tamper-evidence are effectively void, compounding the unverified-self-update RCE.
- **Fix:** Create a dedicated release keystore with a private, secured key (credentials in CI secrets / not committed) and sign release builds with it. Never ship a debug-signed release. Once a real signing cert exists, enforce same-signer verification on downloaded update APKs.

### [security] Cleartext traffic enabled app-wide with no network security config or cert pinning
- **File:** `app/src/main/AndroidManifest.xml`  
- **Where:** <application android:usesCleartextTraffic="true"> (line ~49); build.gradle.kts default API_BASE_URL=http://10.0.2.2:3001/ (line 18)  
- **Problem:** The app is an enterprise CRM carrying student PII (name, email, mobile, lead details), JWT bearer tokens, and call recordings. usesCleartextTraffic="true" allows plaintext HTTP to ANY host, and the build default API_BASE_URL is http://. There is no res/xml/network_security_config.xml and no OkHttp CertificatePinner. If a production build ships with an http:// base URL (or an attacker on the network downgrades/MITMs), every request — including the Authorization: Bearer <JWT> header and all lead PII — travels in clear text and can be captured/replayed. No certificate pinning means even HTTPS is vulnerable to a malicious/compromised CA or a user-installed root CA (common on managed/sideloaded enterprise devices).
- **Fix:** Set usesCleartextTraffic="false" and add a network_security_config.xml that permits cleartext only for the emulator/dev host (debug-overrides) while forcing HTTPS in release. Enforce an https:// scheme on API_BASE_URL for release builds (fail the build otherwise). Add an OkHttp CertificatePinner (or trust-anchors pinning) for the production API host given the PII/enterprise context.
- **Verifier note:** Severity adjusted from critical to high. The cleartext-traffic flag and missing network security config are real and app-wide, but actual plaintext exposure depends on the deployed API_BASE_URL scheme (http vs https), so it is not an unconditional critical. The cert-pinning absence is genuine but is a defense-in-depth gap, not the primary exposure. Proposed fix is sound: set usesCleartextTraffic="false", add network_security_config.xml that permits cleartext only via debug-overrides (emulator/LAN dev hosts), fail the release build if API_BASE_URL is not https://, and add an OkHttp CertificatePinner for the production host.

### [security] Cleartext HTTP traffic globally enabled — tokens, PII and APK over plain HTTP
- **File:** `app/src/main/AndroidManifest.xml`  
- **Where:** <application android:usesCleartextTraffic="true"> ~L49; app/build.gradle.kts apiBaseUrl default ~L16-18  
- **Problem:** android:usesCleartextTraffic="true" is set application-wide and there is no res/xml/network_security_config.xml (Glob confirms none exists), so cleartext is permitted to ALL hosts. The default API_BASE_URL is http://10.0.2.2:3001/ and is injected verbatim into Retrofit's baseUrl, and AuthInterceptor attaches the bearer JWT to every request. On any non-loopback/HTTP deployment the JWT, all student PII responses, call-sync uploads, recording uploads, and the self-update APK download all travel in plaintext, exposing them to passive sniffing and active MITM (which also enables the RCE above). For a sideloaded enterprise app handling PII this is a critical transport-security gap.
- **Fix:** Remove usesCleartextTraffic="true" and add a network_security_config.xml that disallows cleartext (cleartextTrafficPermitted="false") for production, optionally permitting only 10.0.2.2 for debug builds. Force the production API_BASE_URL to https:// and consider certificate pinning for the API and APK-download hosts.
- **Verifier note:** Severity adjusted from critical to high. The cleartext permission is unconditional in code, but actual plaintext-on-the-wire is contingent on a deployment configuring an http:// production host. The shipped default (10.0.2.2:3001) is the emulator loopback alias, which is local-only and not network-sniffable, so out of the box no remote exposure occurs. The defect is the missing transport guardrail (global cleartext allowed + no https/scheme enforcement on API_BASE_URL), which makes an insecure production config trivially possible and silent — a genuine high-severity transport-security gap rather than a guaranteed-exploitable critical. The claim's coupling to APK-MITM RCE is plausible but is a separate finding.

### [security] MANAGE_EXTERNAL_STORAGE all-files over-permission
- **File:** `app/src/main/AndroidManifest.xml`  
- **Where:** <uses-permission MANAGE_EXTERNAL_STORAGE> ~L24-25  
- **Problem:** The app requests android.permission.MANAGE_EXTERNAL_STORAGE (All Files Access). This grants read/write to the entire shared external storage of the device, vastly exceeding the stated need (reading OEM call-recording files in specific Recordings/Call folders). It massively expands the blast radius of any code-execution or library vulnerability (the SQLCipher .so is loaded via System.loadLibrary; the updater installs APKs), lets the process read every other app's media and documents, and is a privacy/compliance liability for an app already holding student PII and call recordings. It will also be rejected by Play and is flagged as high-risk for sideloaded enterprise distribution.
- **Fix:** Drop MANAGE_EXTERNAL_STORAGE and use scoped storage: READ_MEDIA_AUDIO (Android 13+) / READ_EXTERNAL_STORAGE (<=32) with MediaStore queries scoped to the recordings, or the Storage Access Framework (ACTION_OPEN_DOCUMENT_TREE) for OEM folders MediaStore doesn't index. If a narrow OEM folder is truly required, request the minimal access at runtime with clear justification, not blanket all-files access.
- **Verifier note:** Two precision notes, not refutations. (1) The Play-Store rejection point is largely moot: the manifest comment (L18-19) and code state this is a sideloaded enterprise app, so Play review never applies — but the on-device privacy/blast-radius risk is unaffected. (2) The proposed fix to simply drop MANAGE_EXTERNAL_STORAGE is only partially sufficient: scoped storage (READ_MEDIA_AUDIO + the existing MediaStore fallback in queryMediaStore, or SAF) covers Pixel/Samsung/OnePlus, but the code's documented reason for all-files access is exactly the OEMs (Xiaomi/MIUI, Vivo) whose folders are NOT MediaStore-indexed and require raw File scanning of getExternalStorageDirectory(). For those devices a pure-scoped fix would lose functionality, so the correct remediation is SAF ACTION_OPEN_DOCUMENT_TREE on the specific OEM folder (persisted URI permission) rather than blanket all-files access — directionally what the reviewer suggested, but the simple "just drop it" framing understates the OEM-coverage tradeoff.

### [correctness] syncPending() permanently drops calls older than midnight — yesterday's stuck/offline calls are lost forever
- **File:** `app/src/main/java/com/tutelage/crm/counsellor/data/calls/CallRepository.kt`  
- **Where:** syncPending() ~L42-49  
- **Problem:** syncPending() filters unsynced rows to `it.startedAt >= startOfTodayMs()`. Any call that was captured but failed to sync before midnight (device offline overnight, repeated retry failures, app not running) is silently and permanently excluded from every future sync the moment the clock rolls past midnight — its syncedAt stays null but it will never be picked up again. The comment frames this as intentional ('pushing them would flood the CRM with stale history'), but it means a counsellor on poor connectivity loses an entire evening's call records, including answered calls that DO have recordings. This is lost lead-activity data, and pendingSync count will show a non-zero stuck number forever (the unsyncedCount query has no date filter), confusing the user.
- **Fix:** Use a rolling window (e.g. last 24-48h, matching the reconcile() 48h cutoff) rather than start-of-today, or drop the client-side date filter entirely and let the backend dedupe/age-out. At minimum, mark age-filtered rows as 'skipped' so unsyncedCount doesn't report them as forever-pending.
- **Verifier note:** The title's framing ('loses an entire evening's call records') is somewhat overstated. The bug only strands the subset of rows that remain unsynced across a midnight boundary — e.g. device offline overnight, repeated sync failures, or a capture occurring at/after midnight while offline. A device that regains connectivity before midnight syncs normally (the periodic worker runs every 15 min on CONNECTED). But for the affected subset the loss is genuinely permanent with no recovery path, so high severity still stands. One nuance that actually reinforces the bug: reconcile() will finalize a yesterday stale-RINGING row to a correct local status, yet syncPending() still refuses to ship it due to the today-cutoff, so the corrected state never reaches the server.

### [security] FCM click-to-call auto-dials an unvalidated, attacker-controllable number
- **File:** `app/src/main/java/com/tutelage/crm/counsellor/fcm/CounsellorFirebaseMessagingService.kt`  
- **Where:** handleClickToCall() ~L42-84; CallTriggerActivity.placeCall() ~L119-126  
- **Problem:** An FCM data message with type="CTC" causes the app to build a full-screen high-priority notification that launches CallTriggerActivity, which after a 900ms splash calls placeCall() -> Intent.ACTION_CALL on tel:$phone where `phone` comes straight from data["phone"] with zero validation (no numeric/format check, no allowlist, no correlation to a known lead, no server-signature/trust check on the payload). FCM data payloads are not authenticated to the device beyond possession of the FCM sender key; any party able to send to the token (e.g. a leaked server key, or a backend with weak authz on the push trigger) can cause the counsellor's phone to auto-place a call to an arbitrary number — premium-rate/toll fraud, or forced calls to an attacker who then social-engineers. The masking is cosmetic and does not constrain the dialed number. Because CALL_PHONE is held, dialing proceeds without user confirmation other than the brief splash.
- **Fix:** Validate the phone payload (strict E.164/digit regex, length bounds, strip embedded tel separators) and require the leadId to resolve to a lead actually assigned to this counsellor before dialing. Prefer ACTION_DIAL (requires explicit user tap) over auto ACTION_CALL, or require an explicit user confirmation button rather than auto-dialing after a timed splash. Verify CTC payloads carry a server-issued signed token tied to the device before acting.

### [bug] forceSeedToday runs blocking ContentResolver/file I/O on the main thread
- **File:** `app/src/main/java/com/tutelage/crm/counsellor/ui/calls/CallsViewModel.kt`  
- **Where:** forceSyncToday() ~L136-160 -> CallRepository.forceSeedToday() ~L88-105 -> CallLogBackfiller.forceSeedToday() ~L153-279  
- **Problem:** forceSyncToday() launches on viewModelScope (Dispatchers.Main.immediate by default) and calls callRepo.forceSeedToday(), which is a plain suspend function with NO withContext(Dispatchers.IO). ### [robustness] CallSyncWorker swallows all step failures and only ever requests retry — exponential backoff has no run-attempt cap, so a persistent failure retries up to WorkManager's default and never surfaces
- **File:** `app/src/main/java/com/tutelage/crm/counsellor/work/CallSyncWorker.kt`

The top-level steps and the inner loops of reconcile()/backfill are already per-iteration isolated; it is specifically syncPending()'s single batched api.sync call that is all-or-nothing, which is exactly where the proposed per-row isolation fix belongs. Severity medium is appropriate (robustness/operability), not higher.

- **Verifier note:** The defect is real only as minor dead code: loopJob is never assigned, so loopJob?.cancel() in pause()/stop() does nothing, meaning an in-flight fetchNext() is not cancelled (a late return can overwrite the Paused/Done phase — a benign race, not auto-dialing).
